SLIDE 2 · IDEA TITLE

Idea: a neural transceiver that sends meaning, not audio

Template pointers: proposed solution, detailed explanation, how it addresses the problem, innovation and uniqueness. Use the three blocks below as three columns or three rows of bullets, plus one small diagram (the one-line pipeline).

Suggested idea title

iTantra: offline multilingual voice walkie-talkie that transmits text and speaks it back

Proposed solution

  • Android app with on-device STT and TTS for Hindi, Gujarati, Marathi, Kannada, Malayalam, Tamil, Telugu, Odia, Bengali and English.
  • Sender: push-to-talk, pause detection cuts a sentence, STT turns it into text.
  • Only the text (≈100–300 bytes per sentence) goes over Wi-Fi, Wi-Fi Direct or Bluetooth LE.
  • Receiver: speaks it as a voice note; alerts play at maximum volume on the alarm channel and cannot be interrupted.
  • PTT off = phone-call mode (hands-free, both directions).

How it addresses the problem

  • Voice is data-heavy; text of the same sentence is ~800× smaller than raw audio and ~40× smaller than Opus voice.
  • Fits links that cannot carry voice: BLE, congested Wi-Fi, future LoRa bridges (~0.3–5 kbps).
  • Output is still speech, so people who cannot read are included.
  • Everything runs offline on the phone: no tower, no internet, no cloud API.
  • Open-source models and runtimes only.

Innovation and uniqueness

  • Speech → text → speech as a "semantic codec" for low-bitrate radio.
  • Expressive alerts: urgency and emotion travel as a 1-byte tag and are re-voiced on arrival.
  • Live captions on both phones while the speaker is still talking.
  • Self-healing link: LAN → Wi-Fi Direct → BLE fallback, same packet format for an ESP32/LoRa bridge.
  • Planned: sender-voice rendering from a 512-byte voice embedding, and on-device translation so a Tamil speaker hears a Hindi message in Tamil.

Methodology (six steps)

  1. Model selection against three hard limits: covers all 10 languages, open licence, runs on a phone CPU.
  2. Conversion: export to ONNX/GGUF, quantise (int8 STT, Q4_0 TTS), verify on desktop.
  3. On-device pipeline: VAD-gated STT, text pipeline, TTS with streaming playback.
  4. Transport: discovery, tie-break, framing, acknowledgements, fallback order.
  5. Measurement: debug hooks log STT/TTS latency, RTF, memory and CPU as JSON; FLEURS-based WER harness.
  6. Iteration: fix what the numbers show (examples below).

SLIDE 5 · IMPACT AND BENEFITS

Impact and benefits

Template pointers: impact on target audience; social, economic, environmental benefits. Use icons per audience and a benefits grid.

Who it is for

Disaster response teams

NDRF/SDRF, district control rooms and volunteers coordinating when towers are down after floods, cyclones or landslides.

Coastal fishing communities

Boat-to-shore and boat-to-boat alerts in the local language over long-range low-bitrate links.

Rural and low-literacy users

Census 2011 literacy was about 74%; spoken output reaches people a text alert would miss.

Remote field staff

Forest, border, mining, rail track and power-line crews in poor-coverage areas.

Hearing-impaired users

Every message is also shown as large text, with live captions while the sender speaks.

Events and crowds

Melas, pilgrimages and stadiums where the cellular network saturates.

Benefits

Social

  • Alerts in the listener's own language, spoken aloud.
  • The 10 languages cover roughly 85% of Indians by mother tongue (Census 2011), plus English.
  • Works for people who cannot read or cannot see a screen.

Economic

  • No new hardware for phone-to-phone use; ESP32/LoRa bridge costs a few hundred rupees per node (estimate).
  • No airtime or data charges; no cloud or licence fees.
  • Open-source stack can be adopted by state disaster agencies without vendor lock-in.

Environmental

  • Hundreds of bytes per sentence instead of tens of kilobytes: less radio time, lower battery drain on phones and relays.
  • Solar-powered low-power relay nodes become practical.
  • No data-centre inference.
Alignment: supports disaster-risk reduction and inclusive early warning (UN Early Warnings for All, SDG 11 and SDG 13) and India's CAP-based public alerting ecosystem (NDMA SACHET), which iTantra can receive from in a later phase.

A typical spoken sentence lasts about 3 s. The bars compare what it costs to send that sentence in different forms (log scale).

Scale: bar length = log10(bps) / 5.5. Text estimate: ~13 characters per second of speech, 3 bytes per Indic character in UTF-8, plus header. LoRa at SF12/125 kHz carries roughly 250–300 bps and SF7 about 5.5 kbps, so text fits even the slowest setting while voice does not.

FULL SYSTEM · UPGRADE IMPLEMENTATION PLAN

Implementation plan for each upgrade

Each upgrade lists its building blocks, steps, what it depends on, and the number that shows it worked.

A. Efficiency pack (in progress)

  • Blocks: engine manager with lazy load/unload, WavLM-free Mio init, quantised codec, ONNX Runtime memory options, clause splitter for VITS.
  • Steps: load the TTS engine only for the language of the message; unload after 60 s idle (LITE) or 5 min (FULL); init Mio from precomputed voice embeddings; test q8 codec; split text at commas and ~60 characters.
  • Done when: PSS < 1 GB in LITE, idle CPU < 2% in PTT mode, first audio < 0.6 s.

B. Compact binary packets

  • Blocks: 24-byte header (see packet table), per-script static dictionary (top 4,000 words per language from open text), zstd/deflate with that dictionary.
  • Steps: build dictionaries offline; add a codec behind the existing frame interface; negotiate format in the hello frame; keep JSON for debugging.
  • Depends on: nothing. Done when: median sentence ≤ 80 bytes.

C. ESP32-S3 BLE ⇄ LoRa bridge

  • Blocks: ESP32-S3 + SX1262 (865–867 MHz), NimBLE Nordic-UART service identical to the app's, LoRa link layer with fragmentation, ACK and retry; battery + optional solar.
  • Steps: firmware BLE side (reuse app packet format) → LoRa point-to-point → range test (SF7 vs SF12) → enclosure.
  • Depends on: B for small payloads. Done when: 1 km line-of-sight delivery, sentence airtime < 1 s at SF9.

D. Store-and-forward mesh

  • Blocks: message id cache (de-duplication), TTL/hop count, per-node queue, delivery receipts back to origin.
  • Steps: phones and nodes rebroadcast unseen ids with TTL−1; queue while no neighbour; forward when a neighbour appears.
  • Depends on: B, C. Done when: 3-hop delivery demo with receipts.

E. One-tap SOS with location

  • Blocks: localised SOS templates, GNSS fix (NavIC on phones that support it), coordinate → spoken form ("12.97 N, 77.59 E" or nearest named place from an offline gazetteer).
  • Steps: template chips in UI → ALERT packet with lat/lon field → receiver speaks and shows location.
  • Done when: SOS sent in < 2 taps; location spoken in the listener's language.

F. Emotion and urgency transfer

  • Blocks: pitch/energy/speaking-rate features on the sender (no ML needed at first), rule-based urgency score, existing 1-byte emotion tag, TTS style mapping (VITS emotion ids, Mio tags).
  • Done when: listeners pick "urgent" vs "calm" correctly in an A/B test.

G. Cross-language delivery

  • Blocks: IndicTrans2 distilled (≈200M) int8 via CTranslate2 or ONNX; receiver-side translation into the listener's language before TTS; original text kept on screen.
  • Steps: convert model → benchmark on the 870 → enable only in FULL profile.
  • Done when: added latency < 700 ms per sentence; chrF reported on FLORES.

H. Sender's voice

  • Blocks: 10-second enrolment on the sender, speaker embedding (128 floats ≈ 512 bytes) sent once per session with consent, Indic-Mio voice conditioning on the receiver.
  • Done when: listeners recognise the sender more often than with the default voice.

I. Security

  • Blocks: X25519 pairing by QR code, ChaCha20-Poly1305 per packet, Ed25519-signed ALERTs from authorised devices.
  • Done when: unsigned ALERTs are shown as normal messages; tampered packets are rejected.

J. Control-room gateway and CAP

  • Blocks: laptop/Raspberry Pi gateway with a LoRa node, offline dashboard (message log, map, broadcast), CAP 1.2 parser for SACHET feeds when internet is available at the control room.
  • Done when: a CAP alert is re-broadcast and spoken on field phones in their languages.

K. Friendlier, Indian-first interface (in progress)

  • Blocks: onboarding greeting in all 10 scripts, UI localised in 10 languages, language cards in native script, SOS chips, kolam-pattern empty states, credits to Indian open AI research (IISc ARTPARK, IIT Madras SPRING Lab, AI4Bharat).
  • Done when: first-time users complete setup without help in a 5-person test.
